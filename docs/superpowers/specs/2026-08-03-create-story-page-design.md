# Страница создания пользовательской сказки — дизайн

## Цель

Заменить утилитарный экран `/create` на доступную адаптивную «мастерскую сказки» в акварельной стилистике «Ёжика и Лисёнка». Страница сохраняет существующие авторизацию, лимиты, сохранение историй и API-интеграцию, но принимает новые возрастные группы и варианты длины истории.

## Контекст проекта и границы

Проект — статический SPA на HTML, CSS и браузерном JavaScript, собранный `npm run build` и опубликованный на Vercel. Маршрут `/create` уже отображает секцию `#generator` из `index.html`; DOM и навигацией управляет `js/app.js`. Браузерные сервисы подключаются отдельными IIFE-файлами через `window.HF…`.

Генерация вызывается одним синхронным запросом `POST /api/generate-story`. Сейчас ответ содержит всю готовую сказку, без `jobId` и промежуточных статусов. Это решение остаётся: окно ожидания будет открываться немедленно после отправки и переключаться в состояние готовности только после фактического ответа API. Новая фоновая очередь и polling не входят в эту работу.

Не затрагиваются несвязанные маршруты, библиотека, чтение готовых историй, платежи и существующая навигация Header/Footer, кроме активного состояния пункта «Создать сказку».

## Визуальное решение

Утверждённый референс: `pictures/Создание сказки/ChatGPT Image 3 авг. 2026 г., 13_35_35.png`.

Страница сохраняет существующие шрифты сайта и строится на следующих токенах уже используемой акварельной темы:

- тёплый кремовый фон и едва заметная бумажная фактура;
- приглушённый хвойно-зелёный для выделения и основной кнопки;
- охристо-золотой для маленьких звёзд и дружелюбных акцентов;
- серо-бежевые тонкие рамки;
- спокойные естественные тени и радиусы 24–32 px;
- никаких ярких синих браузерных контролов, стеклянных эффектов или декоративного текста внутри изображений.

Композиция:

```text
существующий Header
┌──────────────────── hero ────────────────────┐
│ заголовок и описание │ иллюстрация героев     │
└──────────────────────────────────────────────┘
┌──────────── бумажная карточка формы ─────────┐
│ тема                                          │
│ возраст: [5–6] [7–8] [9–10]                  │
│ настроение + пояснение                        │
│ урок                                           │
│ страницы: [3] [5] [7]                         │
│                 основная кнопка                │
│ Ёжик (декор)                    Лисёнок (декор)│
└──────────────────────────────────────────────┘
существующий Footer
```

На узком экране последовательность строго такая: Header, текст hero, иллюстрация hero, форма. Внутри формы возрастные карточки и декоративные герои перестраиваются так, чтобы не вызывать горизонтальную прокрутку и не перекрывать интерактивные области.

Подготовленные изображения будут перенесены в публичные ассеты с понятными именами. Для каждого будет проверен alpha-канал; смысловая hero-иллюстрация получит короткий `alt`, декоративные изображения — `alt=""`, заданные размеры и responsive-подачу. Оригиналы в `pictures/Создание сказки` останутся нетронутыми.

## Форма и совместимость данных

Поля остаются настоящими HTML-контролами в одном `<form>`:

| Поле | Значение и поведение |
| --- | --- |
| Тема | `topic`, обязательное однострочное поле, `maxlength=80` |
| Возраст | доступная группа radio-карточек: `5-6`, `7-8`, `9-10`; выбранная карточка имеет зелёную рамку, фоновый оттенок и видимую отметку |
| Настроение | существующий `select`: `bedtime`, `adventure`, `friendship`, `bravery`; под ним локализованное краткое описание текущего выбора |
| Урок | `lesson`, обязательное многострочное поле, `maxlength=160` |
| Страницы | доступная группа radio-карточек: `3`, `5`, `7`, c выбранными `5` страницами по умолчанию и пояснением к этому варианту |
| Иллюстрации | существующая логика `yes/no` сохраняется, но не конкурирует с основной визуальной иерархией формы |

Новые возрастные значения передаются во frontend, mock-генератор, API, промпт и сохранённые параметры истории именно как `5-6`, `7-8`, `9-10`. API будет принимать 3, 5 и 7 страниц и ограничивать число страниц семью.

Старые истории со значениями `5-7` и `8-10` не мигрируются и не удаляются. Нормализация истории должна сохранять известное старое или новое значение, а отображение должно использовать отдельную карту подписей. Так библиотека, фильтры и удалённые записи Supabase продолжат открываться без потери возраста.

Отправка блокируется до завершения текущего запроса. Ошибки валидации и API показываются в существующей спокойной тональности; данные формы не очищаются. Лимит остаётся проверяться текущим frontend-сервисом и, для авторизованного пользователя, на сервере. Повторная отправка не создаёт вторую историю и не списывает лимит повторно.

## Ожидание и готовность

После начала синхронной генерации показывается полноэкранный modal overlay:

- задний план слегка затемнён и размывается не более чем на 3 px; прокрутка документа блокируется;
- внутри — бумажная карточка с изображением героев у открытой книги, заголовком «Мы создаём вашу историю…» и нейтральным текстом «Нам понадобится немного времени»;
- пять звёзд соединяются пунктиром; пока ответ не получен, первые четыре этапа циклически и ненавязчиво подсвечиваются, но пятая никогда не выглядит завершённой до ответа API;
- при фактическом ответе звёзды переходят в финальное состояние, заголовок меняется на «Ваша сказка готова!», а главное действие — на «Открыть сказку →»;
- закрытие overlay лишь скрывает интерфейс ожидания и не отменяет уже запущенный запрос в открытой вкладке; при завершении пользователь увидит состояние готовности на странице;
- при ошибке сохраняются значения формы, overlay показывает причину спокойным языком и явную кнопку повторной попытки; автоматическая повторная отправка не допускается.

Modal удерживает фокус, возвращает его к кнопке создания после безопасного закрытия и использует `aria-live` для статуса. Учитывается `prefers-reduced-motion`.

## Локальные задания

Задания не запрашивают AI и не участвуют в API-вызове. Отдельный браузерный модуль хранит структуру задания, наборы данных, выбор следующего задания, проверку ответа и нормализацию ответов.

Каждое задание содержит стабильный `id`, группу возраста, тип, текст, визуальные данные, варианты, вычисленный правильный ответ, подсказку, объяснение и уровень сложности. Генерация избегает повторения подряд; арифметические варианты формируются из проверяемого результата.

- `5-6`: счёт до 10, сравнение, ряд, формы и цвета, поиск пары, простая пропущенная буква; 2–3 варианта.
- `7-8`: сложение/вычитание до 20, умножение на 2/3/5, последовательности, слоги, один логический шаг; 3–4 варианта.
- `9-10`: умножение/деление, выражения в два действия, текстовые задачи, классификация, орфография и маршруты; 3–4 варианта.

На desktop отображаются до трёх карточек: одна активная и две как ближайшие. На mobile выводится ровно одна карточка. Неверный ответ не засчитывается; после второй ошибки открывается подсказка. Верный ответ даёт мягкую зелёную обратную связь и короткую паузу перед следующим заданием. «Можно пропустить» всегда доступно и не влияет на генерацию.

## Границы компонентов

В соответствии с текущей архитектурой это будут небольшие DOM-компоненты и сервисы, а не React-компоненты:

- `index.html` — семантическая разметка hero, формы и шаблон overlay;
- `styles.css` — изолированные классы create-страницы, формы, overlay, заданий и адаптивные правила;
- новый `js/generationTasks.js` — типизированный через JSDoc контракт задач, данные, генератор, проверка ответов и защита от повторов;
- новый `js/createStoryFlow.js` — управление overlay, фокусом, заданиями, состояниями ответа и безопасной очисткой таймеров;
- `js/app.js` — получает данные формы, вызывает существующий backend/mock путь, передаёт реальные события началу/успеху/ошибке create-flow и открывает историю по возвращённому id;
- `api/generate-story.js` — только расширение валидации, лимитов, mock-генерации и AI-промпта для новых значений;
- `js/storyService.js` — совместимая нормализация и отображение старых и новых возрастов.

## Доступность, адаптивность и проверка

Все radio-карточки содержат нативные радио-input; поля имеют связанные label, а состояния получают видимый `:focus-visible`. Минимальная область нажатия — 44×44 px. На 320, 375, 430, 768, 1024, 1440 и 1920 px не возникает горизонтального overflow; клавиатура на телефоне не должна закрывать активные поля.

Тесты будут покрывать полезную нагрузку формы, новые и старые возраста, длины истории, подбор и проверку задач, пропуск, идемпотентность отправки, API-ошибку, доступность overlay и переход к фактически созданной истории. Перед завершением будут запущены `npm run build`, существующие unit-тесты и Playwright e2e-тесты; визуальные результаты проверяются на desktop и mobile.
